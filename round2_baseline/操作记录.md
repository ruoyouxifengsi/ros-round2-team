本项目完成的是“不识别图像的移动控制”：官方发车 → 连续弯道 → QR 区停靠 → 倒车退出 → 随机五桶 → 物块前停靠 → 返程 → 终点停稳。共18个目标点。

QR 与物块阶段明确输出 `IMAGE_SKIPPED`，没有伪造识别结果或播报。机械臂保持官方初始化的收起姿态；相机观察姿态、识别和播报需后续接入。因此控制路线跑通也不等于规则中的完整完赛。

## 2. 在本机 WSL 准备环境

先在 PowerShell 输入：

```powershell
wsl -d Ubuntu-20.04
```

进入 Linux 后，执行：

```bash
bash /mnt/d/ros智能车/round2_baseline/scripts/setup_wsl.sh
source ~/round2_baseline_ws/devel/setup.bash
```

准备脚本使用本机已安装的 Noetic、Gazebo、move_base 和 TEB，创建独立工作空间并编译。已有官方包不会被覆盖。每个新开的 WSL 终端都要执行上面的 `source` 命令。

## 3. 按官方流程手动启动

终端一：

```bash
source ~/round2_baseline_ws/devel/setup.bash
roslaunch round2_baseline baseline.launch
```

这会打开仿真和官方计时器。加 `gui:=false` 可隐藏 Gazebo 窗口，计时器仍启动。

终端二检查是否准备好：

```bash
source ~/round2_baseline_ws/devel/setup.bash
rostopic echo /baseline/ready
```

看到 `data: True`，表示车在起点、已经停稳、里程计和保护节点可用。这不代替裁判的发车许可。

裁判允许发车后，依次执行官方布景程序：

```bash
rosrun car3 random_cones.py
rosrun car3 random_place.py
```

然后在官方计时器输入组号，点击 **Draw**。正式比赛不设固定随机种子，也不因布局不理想擅自重新生成。车模发车后不操作电脑。

开发练习中可以查看：

```bash
rostopic echo /baseline/status
```

| 状态 | 含义 |
|---|---|
| `MOVING` | 正在执行某个目标 |
| `ARRIVED` | 该阶段完成，并确认停稳 |
| `IMAGE_SKIPPED` | 本版跳过图像任务 |
| `FAILED` | 本次失败，查看 detail 和日志 |
| `CONTROL_ROUTE_DONE` | 移动控制流程结束，仍需检查入框证据；不代表完整比赛完赛 |

只在开发测试或裁判允许截车后取消：

```bash
rosservice call /nav_start "data: false"
```

等待车辆停止，再在启动终端按 Ctrl+C。官方计时器的 Stop 不等于取消导航。再次发车需要重新启动场景回到起点，不从终点直接启动下一轮；不要用 `wsl --shutdown` 关闭其他项目。

## 4. 一条命令复现整轮测试

先关闭手动启动的本任务仿真，再运行：

```bash
source ~/round2_baseline_ws/devel/setup.bash
python3 /mnt/d/ros智能车/round2_baseline/scripts/run_trial.py \
  /mnt/d/ros智能车/round2_baseline/evidence/my_trial \
  --cones --seed 42 --timer
```

输出目录必须是新目录。它会启动官方场景、运行两份官方布景程序、通过未修改的官方 Draw 控件发车，并保存全过程。过程中不要人工发速度或修改参数。

- `--seed 42` 只用于练习复现，不会把桶的位置传给控制程序；正式比赛不使用固定种子。
- 不加 `--timer` 是服务接口开发测试，不算官方计时器验证。
- 所有 `--debug-...` 参数只用于诊断，结果明确标记 DEBUG，不能算整轮验收。
- 测试器使用独立端口和互斥锁，只清理自己启动的进程组，不关闭整个 WSL。

测试结束后检查：

```bash
python3 /mnt/d/ros智能车/round2_baseline/scripts/analyze_trial.py \
  /mnt/d/ros智能车/round2_baseline/evidence/my_trial
python3 /mnt/d/ros智能车/round2_baseline/scripts/plot_trial.py \
  /mnt/d/ros智能车/round2_baseline/evidence/my_trial
```

重点看 `analysis.json` 中的 `control_baseline_pass`。它要求完整目标顺序、QR/终点车身入区、终点停稳、官方发车、随机场景及发车后时间检查均通过，并排除 DEBUG 和人工调整过的记录。

| 证据 | 用途 |
|---|---|
| `result.json` | 阶段事件、终态、实际墙钟时间 |
| `analysis.json` | 到位位置、完整车身边界、停稳和整轮验收 |
| `trajectory.png` | 根据激光和里程计绘制的路线 |
| `timer/timer.json` | 官方 Draw 次数及计时器状态 |
| `poses.json`、`snapshots` | 里程计、激光和导航地图原始记录 |
| `control.log`、`simulation.log` | 失败定位信息 |
| `config`、`launch`、`source`、`source_hashes.json` | 本次配置及源码快照 |

启动文件和源码快照使用 `.txt` 后缀，避免被 ROS 识别为重复入口。入框检查使用里程计和官方车模尺寸，不使用 Gazebo 真值，也不是零碰撞证明。

规则的10分钟还包括现场准备与调参。本工具记录的发车后耗时不能单独证明现场总计时合格；增加识别和播报后需要重新测时。

## 5. baseline 是怎样完成的

控制链：

```text
官方 Draw → /nav_start → control.py
                         ├─ 普通路线、QR停靠：move_base + TEB
                         └─ QR退出、终点：里程计直线跟踪 + 地图车身碰撞检查
                                      ↓ /nav_cmd_vel
                               姿态保护 + 转向反馈
                                      ↓ /cmd_vel
                                   官方车模

/scan + /odom → 倾斜扫描门控 → /nav_scan → 导航地图
```

导航读取正常传感器与导航接口，不读取 Gazebo 模型位置，也不读取随机生成日志中的桶坐标或类别。官方计时器和布景程序自身使用的 Gazebo 接口保持原样。

主要修复如下：

| 问题 | 最终处理 |
|---|---|
| 第一轮路线和地图不能直接适用第二轮 | 依据第二轮场地重新设置路线，使用激光滚动地图；QR从开口侧进出，返程走下方通道 |
| 矩形车身轮廓在窄弯中过于保守 | 从官方 URDF 全部碰撞网格测量收臂轮廓，使用包住真实车身并留余量的八边形；未缩放车模 |
| 有转向指令却几乎不转 | 用里程计角速度进行有界比例、积分修正；输出不超过0.65弧度/秒，停止或保护触发时清零积分 |
| DWA在窄弯到点转向失败 | 按赛事教程改用TEB，并给第五弯增加直行到位点 |
| QR附近通用轨迹反复转身 | QR以低速精确进入；退出改为有地图碰撞检查的固定直线倒车 |
| 同一避障间距不适合全部阶段 | 普通窄通道期望间距0.02米；穿桶、物块、返程用0.08米；这不是实际净空保证 |
| 开阔过渡点因厘米级超调卡住 | 锥桶出口、物块前使用5厘米到位容差；其他过渡点通常3厘米 |
| 返程目标与较大避障间距冲突 | 目标移到通道内更宽松的 `(-0.70,1.20)` |
| 终点规划和预计轨迹靠近前墙 | 低速直线停车，目标为 `(-0.25,2.20)`；以完整车身入框和停稳验收 |

直线控制最大速度0.08米/秒。它检查未来约1秒、截至预计停车位置并留少量制动余量的车身范围；车身多边形与障碍方格采用精确相交检查，避免用外接圆近似方格造成误阻塞。障碍、未知格和地图越界都会阻止继续平移。QR退出到位容差3厘米，终点直线停车容差1.5厘米，最终仍按实际车身入框检查。局部地图持续发送完整更新。数据过期、偏航过大、无进展或超时均会失败停车。

TEB的代价地图碰撞检查、完整车身轮廓、姿态保护一直保留。保护在约3°倾斜时暂停，严重倾斜锁定故障。阶段通常最多90秒，总运行保护默认540秒；这些开发保护不替代裁判判定。

- [TEB 官方参数定义](https://github.com/rst-tu-dortmund/teb_local_planner/blob/noetic-devel/cfg/TebLocalPlannerReconfigure.cfg)：轨迹、避障和运动约束设置。

## 6. 自检、修改和双人分工

在加载ROS环境的WSL中：

```bash
cd /mnt/d/ros智能车/round2_baseline
python3 scripts/attitude_guard.py --self-test
python3 scripts/test_docking.py
python3 scripts/verify_assets.py
```

保护自检覆盖启动、速度变化限制、过期数据、冻结时钟、倾斜、扫描门控及转向反馈。直线控制自检覆盖车身内障碍、格子边缘、旋转、未知格、地图边界，以及前进/倒退收敛。文件检查核对官方文件与收臂轮廓包络。

修改路线时，先理解朝向：0朝右、1.57朝上、3.14朝左、-1.57朝下。不要把固定目标放在可能生成锥桶的格点上。每次只改一个明确问题，输出到新证据目录；修改机械臂姿态后必须重新检查车身轮廓。

| 人员 | 负责内容 | 交付检查 |
|---|---|---|
| A：控制与复现 | 维护路线、避障、停车；用不同官方随机布局做复测 | 目标顺序、轨迹、入框和耗时 |
| B：图像与规则 | QR读取、对应物块识别、指定格式播报；本地模型和结果留存 | 使用现场相机结果，接入两个 `IMAGE_SKIPPED` 占位处 |

B按本文从零复现A的控制版本，A核对B的识别数据来源。联调时将图像占位替换为“等待识别完成或超时失败”，然后重新测试全程和总时间。

较早的尝试、失败与中间假设保留在 `evidence/development_notes.txt` 及各测试目录中；它们是历史证据，不是当前操作步骤。
